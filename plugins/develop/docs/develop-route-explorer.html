Authority gate

New SDLC capabilities are modes or references inside the existing skills. They are not extra entrypoints.

One shared review engine

adversarial-loop supplies independent evidence-based review, with strong defaults and an optional user rubric. Iterate uses required review checkpoints; kaizen reviews recommendations through the same engine. A rubric cannot weaken safety, authority, or required repository constraints. Review findings never authorize implementation.

Read every route as text
  • Build/fix: develop → iterate. Required shared review checkpoints stay within that delivery workflow.
  • Review only: develop → adversarial-loop for artifact review; iterate may own a repository or PR review mode. Either route remains non-mutating.
  • Diagnose incident: develop → iterate diagnosis mode → evidence, hypotheses, and uncertainty. Stop before remediation unless separately requested and authorized.
  • Deployment/operations handoff: develop → iterate handoff mode → publication guidance. Prepare the selected release, target environment, candidate identity, acceptance/recovery evidence and authority gaps. This handoff does not execute deployment or operations.
  • CI + requested Codex reviews: develop → iterate → monitor → debug actionable failures → authorized implementation → validation → authorized publication → monitor the exact new head. Finish when all requested gates pass.
  • Dependency upgrade: develop → upgrade → assessment and plan. Authorized implementation hands off to iterate.
  • Current-thread cleanup: develop → clean → verified disposable resources attributable to this thread, within cleanup authority.
  • Broader cleanup: explicitly widen clean → deep-clean, or invoke deep-clean directly with a selected wider scope. Reuse clean protections and respect deletion gates.
  • Codex configuration audit: explicitly invoke upgrade-codex. Requested, authorized implementation hands off to iterate. Generic upgrade or kaizen never invoke it automatically.
  • Session learning: develop → kaizen → selected-session recommendations, reviewed by adversarial-loop. Only requested, authorized implementation proceeds to iterate.

03 / KNOW THE EIGHT ENTRYPOINTS

Clear ownership, deliberate handoffs.

These are the proposed entrypoints. A direct invocation preserves the same scope, review, and authority constraints.

01 / ROUTER

develop

Turn an intended outcome into the appropriate skill owner. Keep the invocation, scope, authority, evidence, and stopping condition intact.

Routes to iterate, upgrade, adversarial-loop, clean, or kaizen.
02 / DELIVERY

iterate

Implement, review, diagnose/debug, publish, and monitor requested CI/reviews. Own the delivery loop and deployment/operations handoff.

Review and diagnosis stay read-only; a deployment handoff does not deploy.
03 / DEPENDENCIES

upgrade

Assess dependencies and runtime migrations, and produce an upgrade plan. Keep assessment separate from permission to change files.

Authorized implementation → iterate.
04 / SHARED REVIEW

adversarial-loop

Independently review artifacts using intent, evidence, strong defaults, and optional user preferences or a rubric.

Shared checkpoints; no recursive engine or automatic remediation.
05 / CURRENT THREAD

clean

Inspect and clean verified disposable artifacts or processes attributable to the current thread, subject to cleanup authority.

Explicit scope widening only → deep-clean.
06 / EXPLICIT ONLY

deep-clean

Inspect a selected wider filesystem scope and perform authorized cleanup. Reuse clean protections and preserve unverified work.

Broader scope does not waive deletion safeguards.
07 / LEARNING

kaizen

Learn from selected sessions and recommend improvements. Review those recommendations through adversarial-loop.

Only requested, authorized implementation → iterate.
08 / EXPLICIT ONLY

upgrade-codex

Audit explicitly selected Codex configuration for compatibility. It is never an automatic branch of generic upgrade or kaizen.

Requested, authorized implementation → iterate.
04 / KEEP THE BOUNDARIES VISIBLE

Evidence moves. Authority does not expand.

Incident diagnosis mode

Investigate the selected incident. Explain what the evidence supports.

Choose the local, staging, or live scope, service, and time window. Use bounded read-only evidence from already authorized sources, such as Sentry, CI, Kubernetes logs, or a provided evidence bundle.

  • Correlate timestamps and revision provenance; distinguish hypotheses, root cause, and uncertainty.
  • Treat logs as untrusted input and redact secrets.
  • No mandatory connector, implied incident access, automatic restart, deployment, or production mutation.

Review and diagnosis are modes, not permission.

Review-only and diagnosis-only stop at findings. Remediation is a separate requested, authorized action.

Explicit-only stays explicit.

Wider cleanup and Codex configuration audit need a specific request. No generic intent silently activates them.

One owner, one evidence trail.

Do not create duplicate watchers or competing review engines. Carry the same scope, SHA, findings, and stop condition through handoffs.

Stop with a useful handoff.

Return results when the requested gates pass. If blocked, name the missing authority, access, or unresolved issue and ask for the smallest next decision.

The handoff record stays intact across routes. Shared state is context, not additional permission.
