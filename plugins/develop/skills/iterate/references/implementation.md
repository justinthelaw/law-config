# Scoped implementation

Use for authorized changes; review-only and prepared-change publication retain their own boundaries. No external workflow framework is required.

1. Establish the requested behavior, affected owners/interfaces and a concrete success check. Read their instructions and current source using [focused source reading](documentation.md#focused-source-reading): combine owner paths with terms, headings or symbols, refine noisy results and inspect relevant bounded sections before widening. Preserve complete coverage where required. For material requirements, connect each acceptance criterion to the evidence that will establish it; keep missing evidence explicit. Separate user requirements from assumptions; ask only when a missing decision materially changes the solution.
2. Choose the smallest coherent change. For a simple fix, a short plan suffices; for cross-component work, identify ordering, contracts, migration and rollback concerns. Honor an explicit plan-only or approval boundary. Reuse an accepted current plan instead of restarting design. For an unresolved consequential choice, record the relevant alternatives, ownership/contracts, selected rationale and protected invariants in the existing intent checkpoint. Simple or already-decided work needs no extra design ceremony.
3. Reuse a suitable checkout/branch. Isolate work when concurrent or unrelated changes could interfere, using native workspace tools or worktrees. Preserve existing work and keep writers on disjoint files; parallelize only independent tasks.
4. Reproduce a defect before changing it. Compare a known-good baseline and trace the actual failing contract. For rendered surfaces, use [visual validation](visual-validation.md) to inspect the actual DOM or native structure and screenshots, reproduce the selected issue and preserve unrelated views and host controls. For behavior changes, use a regression that fails for the relevant behavior and passes after the smallest fix. Tests should assert public behavior, not duplicate the implementation. Reversible prose/metadata changes need proportionate artifact checks.
5. Apply DRY and SOLID through clear responsibilities and stable contracts with their existing owners. Reuse a shared cause's fix instead of adding copies or speculative abstraction. Use [bounded refactoring](refactoring.md) when requested or justified within the affected scope, not as automatic polishing. Preserve APIs and security controls; investigate unexpected failures before stacking retries or workarounds.
6. Follow [validation evidence](validation.md) and the shared review checkpoints. A fresh result establishes only the artifact and environment actually tested. Hand authorized publication to [publication](publication.md); local completion does not imply deployment.

Compatible installed planning, debugging, testing or review skills can supplement this process. For example, [Superpowers in the Codex marketplace](https://github.com/openai/plugins/tree/main/plugins/superpowers) can provide scoped guidance such as `systematic-debugging` when installed and compatible. Verify tool support and availability; keep Iterate as the implementation/delivery owner and preserve the current scope, authorization, review checkpoints and budget. This optional handoff does not import the entire external workflow or require installation.
