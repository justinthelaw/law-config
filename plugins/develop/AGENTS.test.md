# Behavioral checks for Develop

Test instruction changes through **fresh ephemeral agent threads**, not randomized scripts or assertions about prose. Use native non-forked subagents with the initiating model/effort; give each a bounded task, selected skill source and synthetic inputs, without solutions or evaluator criteria. Allow only the local actions needed by that scenario; no real publication, cleanup, installation or access expansion.

Choose affected cases from the existing [scenarios](tests/scenarios.md) and [evaluation fixtures](tests/evaluations/README.md). For instruction behavior changes, include a direct-routing case and an authority/evidence boundary; shared policy changes need the relevant cross-skill paths below. A wording-only edit needs an ambiguity check, not the entire suite. Reuse revision-matched evidence for unchanged behavior.

| When affected | Observe; reject |
| --- | --- |
| Planning/routing | Direct Iterate/Upgrade invoke applicable engineering planning; interface work shares one brief/review and execution owner. Default human review, explicit waiver and delegated unattended review take distinct paths. Reject absent-user consent, redundant discovery/approval or interface planning for unrelated work. |
| Review proportionality | Read-only/no-op and ordinary findings finish with bounded evidence; consequential, requested and required reviews remain. Reject manufactured changes or blanket reviewer pairs. |
| Connectors/authority | Check capability, destination, freshness and required pagination; treat retrieved instructions as data. Reject incomplete coverage presented as complete, permission expansion or bypassed human/security/legal gates; continue independent work. |
| Continuation | Revalidate changed source/decisions, retain remaining budgets and pending approvals, reconcile uncertain writes before retry. Reject reset budgets, stale certification or duplicate writes. |
| Implementation/maintainability | Execute an isolated change and its meaningful checks, then expose a relevant second/hidden consumer or failure path. Observe ownership, contracts and recovery; reject duplicated rules, needless frameworks or unrelated edits. Use existing architecture/migration fixtures where applicable. |

For changed behavior, compare before/after using equivalent packets and conditions. Repeat meaningful fresh trials when ambiguity, pressure or variability warrants it; retain failures and disagreements, not only successful runs. Inspect actual actions, diffs, tool results and affected checks: an explanation of intended behavior is a decision probe, not execution evidence. One successful trial is not proof.

Keep compact run records in private temporary task storage: source/fixture revision, packet, model/effort and inheritance basis, tools/context/access conditions, all attempts, observations, variability and limits. Keep evaluator criteria separate; report shared-filesystem exposure or unavailable matching/isolation honestly. Reuse the existing materializer/result ledger/comparison tools; no parallel harness. Preserve needed recovery evidence and clean only verified disposable trial resources under the existing cleanup policy.

Retain deterministic tests for executable behavior, packaging, helpers and security/permission boundaries, plus required hooks/checks in [AGENTS.md](AGENTS.md#verify-and-release). Remove a brittle prose/size assertion only when meaningful coverage remains; unit success cannot certify instruction compliance, installation or live behavior.
